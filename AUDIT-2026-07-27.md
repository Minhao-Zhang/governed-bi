# Adversarial audit — governed-bi

**Date:** 2026-07-27 · **Commit:** `fbc0129` · **Working tree:** clean, unmodified by this audit

Seven independent reviewers were run against the repo with different hats: hostile
security red-teamer, reviewer-2 methodologist, structural architect, documentation
fact-checker, serve-path bug hunter, QA skeptic, and production SRE. Every claim below
is anchored to a line someone read. Nothing was inferred from a docstring.

**Verification legend**

| Mark | Meaning |
|---|---|
| **[V]** | I reproduced this myself — ran the code, diffed the output, or executed the probe |
| **[A]** | A reviewer anchored it to specific code; I read the anchor but did not re-run it |

**Baseline facts.** 31,929 lines of source across 96 files. 27,239 lines of tests across
90 files. 17,606 lines of English + Chinese docs. `uv run pytest` → **1383 passed, 13
skipped, 1 xfailed in ~10s**, green, offline, order-independent across seeds. The corpus
contains **one** database subtree (`beer_factory`, 17 assets).

---

## The thesis, in one paragraph

The engine is more real than a cynic would guess. The guardrails block every SQL
injection shape thrown at them. The corpus validator and CI job exist and run. The
eval harness has a treatment-delivery check most published text-to-SQL work lacks.
The problem is not that the system is fake — it is that **the documentation describes a
different, safer system than the one in the repo, and does so in language that leaves no
room for doubt.** Across the English docs there are **314 unhedged absolutes**
(*never* / *always* / *guarantee* / *cannot*) against **49 hedges** — a 6.4:1 ratio **[V]**.
Under that confidence sit a read-only claim that is a no-op on the production engine, an
audit trail that can be skipped, an assurance stamp that measures nothing about grounding,
a curator whose adversary never rejects anything, and an evaluation harness that
structurally cannot return the answer "the corpus does not help."

The single most useful reframe: **most of these findings are already written down
somewhere in the repo — in a module docstring, a code comment, or a plans/ file. The
canonical docs then say the opposite in the present tense.** The codebase is honest with
itself and oversells to the reader.

## Part 1 — Critical findings

Ranked by how badly a reasonable reader would be misled about safety or correctness.

### C1. Postgres "read-only" is a complete no-op **[V]**

`gateway/connectors/postgres.py:70` connects with `autocommit=True`, then `:76` sets
`self._conn.read_only = True`.

In psycopg 3.3.4, `read_only` is consumed in exactly one place — `_get_tx_start_command()`
(`_connection_base.py:550-562`), which assembles the `BEGIN ... READ ONLY` statement. Every
caller reaches it through `_start_query()`:

```python
# psycopg/_connection_base.py:538-541
def _start_query(self) -> PQGen[None]:
    if self._autocommit:
        return
```

No transaction is ever started, so `READ ONLY` is never sent. There is no
`SET default_transaction_read_only` anywhere — the only session `SET`s are
`synchronize_seqscans` and `search_path` (`postgres.py:97,102`).

**On Postgres and Redshift there is zero database-level write protection.** The Python
string checks are the only barrier.

The module docstring (`postgres.py:12-15`) claims the opposite verbatim: *"Read-only is
security-critical: the gateway trusts this connector to make writes fail... `psycopg` (v3)
makes every subsequent transaction on a connection read-only once
`connection.read_only = True` is set, so INSERT / UPDATE / DDL raise at execute time."*

The test that should have caught it asserts that Python's `=` operator assigns:

```python
# tests/test_postgres_connector.py:133-136
conn = FakeConnection()                     # .read_only is a plain attribute
PostgresConnector("postgresql://x", connection=conn, read_only=True)
assert conn.read_only is True
```

SQLite is genuinely protected (`PRAGMA query_only = ON`, `sqlite.py:57`) and
`tests/test_connector.py:135` proves it with a real `pytest.raises`. The documented
production engine has no equivalent.

> I initially scored this as holding up, based on reading the connector rather than
> psycopg's dispatch. It does not hold up.

### C2. `semantic_assurance = grounded` does not mean grounded **[V]**

The README sells a two-axis stamp: *"`safety_clearance` (did it pass the guardrails) and
`semantic_assurance` (how well-grounded)"* (`README.md:28`).

What the code computes (`analyst/answer.py:137-149`):

```python
def semantic_assurance(signals: UncertaintySignals) -> SemanticAssurance:
    """...A clean run is ``grounded`` (no flag fired, NOT verified correct)...
    Uncalibrated heuristic, tuned against the eval."""
    if signals.fenced_raw_fallback:  return SemanticAssurance.unverified
    if signals.any_fired():          return SemanticAssurance.heuristic
    return SemanticAssurance.grounded
```

The five signals are `low_confidence_join`, `suspect_in_scope`, `fenced_raw_fallback`,
`corrective_rag`, `repaired`. **None is a function of retrieval quality, coverage, or
whether the corpus actually covered the question.** One of them, `corrective_rag`, has no
writer anywhere in `src/` — a signal the stamp advertises and never receives.

There is **no relevance floor anywhere in retrieval** — grep for `min_score|threshold|floor`
across `retrieval/` returns nothing. `retrieve()` takes the top `top_k=8` with no minimum,
and with an embedder `EmbeddingIndex.rank` keeps every asset scoring `> 0`, so the budget
cut always returns 8 tables regardless of topicality. `assemble` never checks
`len(retrieval.table_ids)`.

**Concrete failure [A]:** ask "how many employees do we have?" against the beer_factory
corpus, which has no employee table. Retrieval returns 8 arbitrary tables. The agent writes
`SELECT COUNT(*) FROM customer`, it clears all five layers on the first attempt, executes,
and the narrator renders it in plain English. The delivered answer carries
`safety_clearance=True`, `semantic_assurance=grounded`, `tier=governed`,
`uncertainty_flags=[]`.

`docs/analyst.md:106` does state this correctly and at length. `README.md:28` does not, and
the field name says the opposite of what it measures.

### C3. The measured numbers came from a fail-**open** configuration **[V]**

Three documents assert, identically and without hedge: *"Out-of-scope, missing coverage, or
a tripped guardrail returns a refusal or a clarifying question, never a confident wrong
number"* (`README.md:25-26`, `docs/README.md:84`, `docs/architecture.md:13`).
`docs/analyst.md:123` is a four-word paragraph: *"Never a confident wrong number."*

`analyst/governance.py:696-745` — graded delivery. When `grade_semantic_failures` is on and
the SQL failed **L4 or L5**, the system re-executes it and returns narrated rows.

Serve default is `False` (`config.py:155`). But **both eval drivers hard-code it on**:

```
src/governed_bi/eval/run_datalake.py:3795:   grade_semantic_failures=True,
src/governed_bi/eval/run_experiment.py:734:  grade_semantic_failures=True,
```

Both also set `hard_block_suspect_columns=False` (`run_datalake.py:3794`,
`run_experiment.py:733`), turning off the L3 suspect-column block.

**Every number this project has produced describes a configuration that differs from the
advertised fail-closed posture in two safety-relevant ways, and no doc says so next to the
fail-closed claim.**

Worse, graded delivery re-checks with `allowed_tables=None`, which **skips L4 entirely**
(`guardrails.py:754`). Reviewer-verified probe **[A]**:

```
sql = "SELECT salary, ssn FROM hr.employees"      # only beer.sales was licensed
with L4:              passed=False  term_semantics  "table outside the retrieved scope"
allowed_tables=None:  passed=True   <-- executed and delivered
```

Since L3's allowlist is built from the **whole** corpus, and `run_datalake.py:703` pools 69
schemas into one corpus, L4 is the only cross-schema scoping layer — and graded delivery is
designed to bypass it.

### C4. The "read-only audit API" has an unauthenticated write endpoint, on by default **[V]**

`README.md:107` lists *"the **read-only** audit API"* among what is built and tested.
`docs/viz.md:5-16`: *"The **read-only audit surface**... Editing the corpus and opening PRs
is intentionally not built here."*

`api/app.py:295` — `@app.post("/corpus/edit")` → `write_corpus(...)` at `:406`. The only
gate is `stack.can_edit` = `settings.allow_edit`, and the committed default is **true**:

```
governed_bi.toml:84   allow_edit = true
config.py:214         allow_edit: bool = True
```

There is no authentication anywhere in the API. `Depends|Authorization|Bearer|APIKeyHeader`
returns zero hits repo-wide; the only middleware is CORS (`app.py:116`).
`api/schemas.py:295` publishes `identity: str | None = None  # accepted but not enforced` —
a decoy field in the OpenAPI schema.

Three concrete exploits **[A]**: flip `governance.excluded` back to false on a redacted
asset and re-POST it; overwrite a `note` asset to inject ~16 KB of attacker text into every
subsequent user's system prompt under `## Governance notes (must honour)`; poison few-shot
SQL. Effect lands on restart (`stack.py:226` snapshots the corpus), which makes it
persistent-and-delayed, not safe.

Path traversal on this endpoint **is** genuinely fixed, three layers deep **[A]** — which is
the tell that someone reviewed the endpoint's inputs while nobody questioned whether the
endpoint should be reachable at all.

### C5. There is no adversary; nothing has ever been rejected **[V]**

`docs/curator.md:49`, present tense: *"Adversary: an independent agent that tries to refute
each proposed Inference asset before it is committed... Verdict: accept / revise / reject."*
`curator.md:78-81` draws a mermaid diagram with `reject → Propose` and `revise → Propose`
edges.

Four independent confirmations that neither edge exists:

1. **The real path's adversary is explicitly non-gating.** `curator/pipeline.py:405`:
   ```python
   """Structural adversary as a *signal* (design §1): record findings, never gate."""
   ```
   It writes findings to a sidecar and subtracts `0.1 * len(notes)` from confidence. Then
   `bag.write(out_root)` runs unconditionally at `:753`. **Every asset ships.**
2. **The gating loop is dead code.** `loop.curate` (`loop.py:65`) is the only function that
   promotes `proposed → draft` on a green pass. `grep -rn "curate(" src/` returns exactly
   one hit: its own definition. `pipeline.py` never imports it.
3. **The LLM adversary does not exist.** `adversary.refute` (`adversary.py:112`) raises
   `NotImplementedError` for every non-note asset. Nothing in `src/` calls it.
4. **The authoring model is told to review itself.** `prompts/registry.py:137`:
   *"You are the curator: you author the semantic layer... **and you are your own
   adversary**."*

There is no accept criterion. A corpus with dangling references and missing physical tables
is written and served.

### C6. The LLM can forge the human certification stamp **[V]**

`README.md:22` describes the corpus as *"curator-authored and human-audited."*

Every one of the six curator write tools exposes `certified: bool` and `answered_by: str`
**as model-callable parameters** (`deep_agent.py:122,141,159,181,...`). They flow to:

```python
# curator/asset_bag.py:765-777
def _audit(self, *, certified=False, answered_by=None, existing=None) -> Audit:
    if certified:
        return _inference_audit(
            model=self.model_name,
            source=ProvenanceSource.human,       # <- a lie
            status=ProvenanceStatus.certified,   # <- "human signed off (prod only, D6)"
            by=answered_by,                      # <- free text the model chose
        )
```

An LLM can emit `upsert_metric(..., certified=True, answered_by="Jane Chen, Finance")` and
produce an asset indistinguishable on disk from a human certification. It also **discards
the prior audit** — the `existing` branch is only reached when `certified` is false.

Phase B makes this the default: `build_curator_agent(..., certified_writes=True)`
(`pipeline.py:967`) forces it on **every** write, including in `_validate_fix_pass`
(`:998`) — so the pass that repairs dangling references stamps its repairs
`source=human, status=certified`.

**No human gate is enforced anywhere.** `auto_accept_corpus` appears in `src/` three times:
its declaration, the two `for_env` branches, and `provenance.py:87` where it is hashed into
a config fingerprint. It gates nothing. At serve time `ProvenanceStatus` is used in exactly
one place (`note_inject.py:32-35`) as a **sort key**, not a filter — a `proposed` asset and
a `certified` asset are served identically.

### C7. Nothing validates that a curator-authored asset is *correct* **[V]**

What `validate_corpus` checks: ID regex, duplicate IDs, `(schema, physical_name)`
uniqueness, reference resolution, note budgets, C5 excluded-identifier withholding, and
join `ON`-clause column membership.

What it does not check, at all:

- **`MetricAsset.expression` is never parsed, never executed, never type-checked.**
  `SUM(price)` when price is in cents, or `AVG(rate)` when rate needs weighting, passes
  green and becomes authoritative guidance in the analyst prompt.
- **A join is never test-joined.** `upsert_join` defaults `cardinality="many_to_one"`
  (`deep_agent.py:120`), and naming-convention guesses (`pipeline.py:128-149`) take that
  default with zero evidence. A wrong cardinality is a silent fan-out and a doubled aggregate.
- **A description is never checked against anything.** "One row per completed order" on a
  table that is one row per order *line* passes forever.
- **Few-shot SQL is never executed.**

**And the CI gate skips both of its semantic checks [V].** CI runs
`python -m governed_bi.corpus.cli`, which calls `validate_corpus(corpus.assets)` with **no
`connector` and no `train_refs`** (`cli.py:64`). `validate.py:271-272` gates
`_check_physical_existence` on `connector is not None`, so it never runs. Output:
`CI green: 17 assets, 0 findings.` — which reads as a semantic gate and is a YAML
reference-integrity pass.

The leakage guard is self-declared dead. `validate.py:26-41`, verbatim: *"**This one
currently protects nothing, and should not be cited as though it does.**"*

**Nothing closes the loop.** No serve-time feedback, no drift detector, no periodic
re-validation. A confidently-wrong asset poisons every future answer and the system has no
mechanism — built or seamed — that would notice.

### C8. The eval harness cannot return "the corpus does not help" **[A]**

A grep across `docs/` for `pre-regist|falsifi|abandon|stopping rule|does not help` finds:

- `docs/design-decisions.md:261` — pre-registration explicitly **rejected**: *"it needs
  pre-registered breakpoints plus snapshot pinning, so it is deferred as unnecessary for a
  first result."*
- `docs/plans/experiment-runbook.md:479-503` — the "Before quoting anything" checklist.
  Every item is a condition for quoting a **positive** delta.
- The closest negative statement (`experiment-runbook.md:611-614`) says a delta that dies on
  the twin-free stratum is *"not established"* — never *"the corpus does not help."*

**The asymmetry is structural.** `eval/treatment.py` and `index._undelivered` make a **null**
result non-quotable whenever treatment delivery cannot be positively shown. That is the best
idea in the harness. But there is no rule of equal weight that can make a **positive** result
non-quotable: no check that wins concentrate on empty-gold questions, no bound on degenerate
answers, no check that injected context encoded a train twin's answer. `treatment.py:9-25`
narrates two prior nulls overturned by delivery bugs — the machinery built from that
experience runs in exactly one direction.

Layered on top are at least eight prepared explanations for a null, including a pre-declared
fallback claim lane (`experiment-runbook.md:410-417`): if EX does not move, the claim
relocates to `semantic_assurance`.

## Part 2 — Evaluation methodology

The harness is unusually self-aware: the EX denominator is right (refusals score 0, so a
refuse-everything arm scores 0.0, **not** 1.0 **[A]**), the paired tests are correct (exact
binomial McNemar, Holm over the right family, CIs on the per-question unit **[A]**), arm
isolation is genuinely tight (only `corpus=` differs in `make_serve_worker_factory` **[A]**),
and `oracle_sql` measuring the grader's own ceiling is an instrument most harnesses lack.

The problems are all of one shape: **the harness detects a problem, records it, and does
nothing.** `index.py:22-23` says it outright — *"Both are advisory in the sense that nothing
blocks you."* Leakage detected, treatment not delivered, arms crashed, schemas missing — all
produce the same observable behaviour: a string in `not_quotable_because`, a print, exit 0.
No CI job invokes any of it.

### E1. `--resume` silently resamples only the losing draws **[V]**

```python
# eval/run_datalake.py:3341-3351
if resume and not replay_crashed:          # replay_crashed defaults to False (:3259)
    crashed = [r for r in done_rows if classify_row(r)[0] is Outcome.crashed]
    ...
    _write_jsonl(out_path, [r for r in _read_rows(out_path)
                            if str(r.get("question_id")) not in crashed_ids])
```

The stale row is **physically deleted from the artifact**, then re-served. A crashed row
scores `correct=False`. `index.quotable` fails any run with non-zero `crash_rate`. The code's
own comment states the loop (`:3329-3332`): *"`quotable()` refuses any arm with a non-zero
crash rate, so one bad turn in 10,150 disqualifies the result."*

So the prescribed recovery is: run → `crash_rate > 0` → not quotable → resume → crashed turns
get a fresh sample → `crash_rate: 0.0` → quotable. **Only losing rows are resampled, only for
the arms that crashed.** `power.py:8-9` measures that a replicate flips 135 of 2030 answers
(~6.7%), so re-serving 180 laundered rows buys roughly 6–12 questions in expectation, free,
in one direction.

**No counter records that it happened [V]** — `grep -rn "n_re_served|re_served|resampled"
src/governed_bi/eval/` returns nothing. The only trace is a stdout line. No test references
`replay_crashed`.

### E2. Grading manufactures correct answers **[V]**

Reproduced against the real normaliser:

| Probe | Result |
|---|---|
| empty result vs empty gold | **match** |
| `SELECT 1` vs gold returning scalar `1` | **match** |
| `'5'` vs `5` (lenient coercion) | **match** |
| `0.1+0.2` vs `0.3` | no match — **no float tolerance** |
| `[(1,),(1,)]` vs `[(1,)]` | no match — duplicates preserved |

`hash_grade.py:311-321`: `correct = (h_lenient == gold.hash_lenient)`. Nothing counts the
empty-gold case. The row already records `gold_nrows`; `_summarise_rows` already computes the
mirror statistic `n_wrong_but_nrows_match`. There is no `n_correct_with_empty_gold`.
`error_taxonomy.py:409` even defines a `both_empty` label that is unreachable from the
correct-answer branch.

**Why this is not arm-neutral:** the curated corpus injects suspect-column caveats and decoy
warnings. Every one pushes the model toward narrower predicates. A narrower predicate returns
zero rows more often. On questions where gold is also empty, over-filtering is a free correct
answer — and "the corpus helps" and "the corpus makes the model over-filter into free passes"
produce the identical signal.

Also: the two graders in this repo disagree by definition **[A]**. `ex.py:28` builds a
`frozenset` (dedupes rows); `hash_grade.normalise_result` sorts a list (preserves
multiplicity). `ex_crosscheck_agree_rate` is published as a sanity signal; any duplicate-row
result makes it drift for definitional reasons. And `ex.py:8-11` claims to implement *"BIRD's
official EX"* (set-based) while the grader producing every headline number is stricter than
the benchmark it names.

### E3. The decoy-defense mechanism uses train labels to build the artifact under test **[V]**

`curator/pipeline.py:683` unconditionally calls
`_mark_columns_absent_from_gold(bag, [it.sql for it in train_items])`. Its own docstring
(`:490`): *"Heuristic decoy defense: columns never referenced by train gold SQL."* Every
non-unique column absent from train gold SQL is marked
`"DO NOT USE — never referenced by working train SQL (likely unreliable)"`.

`build_curated_corpus` is the curated-arm builder in **both** eval drivers
(`run_experiment.py:794`, `run_datalake.py:2664`), and the `train` split feeds it directly
(`run_datalake.py:2694`).

Train and test come from the same database and the same question distribution, so the test
set's gold columns overlap heavily with train's. The metric that improves most dramatically
— decoy-column touches → 0 — is therefore substantially determined by the construction, not
by the model reasoning better over a semantic layer. The columns are rendered to the model
as explicit `[SUSPECT - DO NOT USE: ...]` lines under a `## Reliability caveats` heading
(`context.py:327-328,389`).

This is not leakage in the strict "test answer in the corpus" sense, and the mechanism is
honestly named in code. But it is label information from the train split shaping the artifact
under measurement, and no doc frames the decoy result that way.

**Same mechanism, catastrophic for real users [A]:** with no train SQL — which is every user
the README addresses — every non-unique column is marked DO NOT USE. Reproduced against the
shipped fixture: **53 of 61 columns**. In the dev profile `hard_block_suspect_columns=True`,
so a user who follows the README gets a corpus that hard-blocks 87% of its own columns.

### E4. Infrastructure failures land in the accuracy number **[A]**

`hash_grade.py:293-310` executes the prediction and catches every exception as
`error = f"exec_error:{type}: {err}"`, `correct=False`. Then `stages.py:239-243` classifies
any `exec_error:` prefix as **not a crash** — the row becomes `Outcome.answered`,
`crash_rate` is unaffected, `quotable()` returns True.

The classifier cannot distinguish `UndefinedColumn` from
`OperationalError: server closed the connection` or a 60-second gateway timeout.

**Scenario:** autovacuum or lock contention pushes 40 queries past 60s during the `curated`
arm and not during `baseline`. Those 40 become wrong answers for `curated` only.
`crash_rate: 0.0`, `quotable: true`, and the delta moves by 40 questions — roughly *five
times* the MDE the run computes from its own replicate.

Related: `Gateway` carries a `truncated` flag and `score_sql_hashes` never reads it. A
prediction truncated at 200,000 rows is hashed as if complete.

### E5. Other measurement gaps **[A]**

- **The MDE is derived from serve noise and applied to a corpus-level treatment.**
  `power.py:110-119` says it: *"the corpus is the treatment: each `(arm, db)` corpus is one
  draw from a stochastic curator agent, n=1."* `measure_floor` re-serves the *same* corpus.
  The resolution figure the whole report is read against bounds only decoding noise.
- **The corpus is not a comparability key.** `COMPARABILITY_KEYS` (`index.py:47-55`) covers
  split, model, prompt hash, routing knobs — not the corpus, the entire independent variable.
  There is no corpus content hash anywhere; `corpus_release_hash` reads `.git/HEAD` of the
  **code** repo (`provenance.py:116`) and returns `"unknown"` with no error when absent.
- **Temperature is neither pinned nor recorded.** `grep -rn "temperature" src/` finds only
  prose. `power.py:5-7` notes the proxy drops it.
- **`--limit`-style attrition is silent.** `_assert_train_test_disjoint` enforces question-id
  disjointness only. Byte-identical question text across splits is documented in code
  (`oracle.py:105-110`: *"five questions appear in both the train and test splits with
  byte-identical text"*) and checked by nothing.
- **`eval_refuse_gate` is never called from the scale driver**, and its one call site passes
  `answerable=[]`, so `false_refusal_rate` is `0.0` by construction. The "fails closed" half
  of the claim has zero evidence at 69-schema scale.
- **`single_variable` means "adjacent rung", not "one mechanism".** `baseline → seeded`
  reports `single_variable: true` while `arms.py:84-85` states it changes three things at
  once. `docs/measurement.md:693-694` asserts *"each step changes exactly one thing"* and is
  refuted 20 lines later in the same file.
- **Nothing exits non-zero.** The only `SystemExit` in `eval/` returns a hardcoded 0.
- **`note_gates.py` (297 lines) has no production caller**, and builds its gold pairs from
  the table descriptions it then retrieves against — a gate that can only fail if the
  embedder is catastrophically broken.

## Part 3 — Security and the guardrails

### What holds up — tested, not assumed **[V]**

I built the real allowlist from the committed corpus and probed `check()` with a valid
baseline. Every one of these was **blocked**, at the correct layer:

multi-statement (`; DROP`) · `WITH x AS (DELETE ...)` · `SELECT ... INTO` · `pg_sleep` ·
`pg_read_file` · `lo_import` · `dblink` · `COPY ... TO PROGRAM` · `CREATE FUNCTION` ·
INSERT / UPDATE / GRANT · `SET ROLE` · comment obfuscation (`SELECT/**/col`) ·
string-literal smuggling · `SELECT *` and `t.*` · unconstrained cross join · suspect-column
access · unparseable SQL · empty string · an empty allowlist (fails **closed**).

Also verified: `SET statement_timeout` is real and server-side (`postgres.py:221`); the
`pg_`/`lo_`/`dblink` prefix denylist works through schema qualifiers and casts **[A]**; L3 is
scope-aware and handles `NATURAL JOIN`, `USING`, and unicode homoglyphs **[A]**; there is no
`eval`/`exec`/`pickle`/`shell=True`/unsafe `yaml.load` in `src/` **[A]**; run-log redaction is
a real whitelist **[A]**; path traversal is genuinely fixed **[A]**.

**This is a competently written SQL-shape filter.** The findings below are about what it is
not.

### S1. The L3 allowlist is case-sensitive, and 100% of identifiers are mixed-case **[V]**

`guardrails.py:82-106` builds keys `{schema}.{physical_name}.{column}` from the corpus
verbatim. `middleware.py:342` passes `set(self._allowlist.allowed)` with no normalization.

Measured: the beer_factory allowlist has 26 entries, **26 of 26 not all-lowercase**. The
fixture DB has 61 columns, **61 of 61 mixed-case**.

Probe against the real allowlist, `dialect="postgres"`:

```
SELECT customerid FROM beer_factory.customers   ->  BLOCK  "column not in the allowlist: customerid"
SELECT CustomerID FROM beer_factory.customers   ->  PASS
SELECT CUSTOMERID FROM beer_factory.customers   ->  BLOCK
```

**Postgres folds unquoted identifiers to lowercase — those three are the same query to the
server.** The verdict depends on the letter case the LLM happened to emit.

Compounded by `middleware.py:315-317`, which runs `sqlglot.transpile(..., identify=True)` —
quoting every identifier while preserving the model's case. A lowercase-emitting model
produces `"customerid"`, which is a hard DB error on Postgres even if it cleared L3.

**Consequence:** an unknown, case-driven share of correct SQL is refused, and the refusal is
attributed to coverage or governance in the eval rather than to a string comparison.

### S2. SELECT-shaped write primitives pass all five layers **[A]**

All `PASS` with `dialect="postgres"`:

```
SELECT setval('ds.myseq', 999) AS z
SELECT nextval('ds.myseq') AS z
SELECT public.do_evil() AS z
```

`setval`/`nextval` are genuine data modifications. Arbitrary UDFs — including
`SECURITY DEFINER` ones that do DML — are unrestricted. The denylist is a blocklist of ~25
names plus prefixes; anything else is permitted. `guardrails.py:158-159` flags this itself:
*"A positive allowlist of permitted functions would be more robust; deferred as a follow-up."*
Chained with C1, that deferral is the write path to a production warehouse.

### S3. `check()` raises instead of blocking, at trivial input depth **[V]**

`guardrails.py:1-8` claims *"Ordered, fail-closed on any layer"*; `:257-260` claims it
*"always yields a fail-closed verdict instead of an unhandled exception."* It catches only
`SqlglotError` (`:264`). At the default recursion limit of 1000:

```
depth  50 -> RAISED RecursionError  <-- escapes the guardrail
depth 100 -> RAISED RecursionError
depth 200 -> RAISED RecursionError
```

`SELECT ((((...50 deep...)))) AS z` — a short string a model can emit — makes `check()` raise.
`middleware.py:342` has no `try/except` around it. No data leaks (the raise precedes
execution), but it breaks a different stated invariant: the ledger dicts are constructed
*after* `check()` returns, so this produces **a hole in the audit trail** and a 500.

### S4. `inspect_schema` lets the agent self-license any table in the corpus **[A]**

`analyst/tools.py:285-306`: `inspect_schema(table_id)` resolves via `_table_by_id`, which
scans **all** `corpus.assets` with no scope restriction, then emits
`Command(update={"licensed": [asset.id]})`. `GovState.licensed` is
`Annotated[list, operator.add]`, and `middleware.py:340` feeds exactly that into L4's
`allowed_tables`.

`guardrails.py:657-659` describes `allowed_tables` as *"the tables surfaced by retrieval and
their join-plan Steiner points."* That is only the seed; the agent grows it at will.
`docs/analyst.md:91` — *"a rogue agent cannot self-authorize an `excluded` table"* — is
narrowly true and broadly misleading: it can self-authorize any of the thousands of
non-excluded tables in a pooled corpus. `middleware.py:166-168` concedes the gap.

### S5. Corpus content is injected as authoritative instruction with zero sanitization **[A]**

`note_inject.py:264-276` renders notes verbatim; `context.py:393-398` emits them under
`## Governance notes (must honour)`. The system prompt (`registry.py:79-81`) tells the model

delimiting, no escaping, no length cap on `body`.

`grep -rn "prompt injection" docs/ src/` returns exactly one hit — `note_inject.py:1`, using
the phrase to mean *inserting* notes. **The corpus is treated as fully trusted input and the
threat is not modeled anywhere.** Chained with C4 (anyone can write the corpus) this is the
primary poisoning vector. Second-order: `llm_proposer.py:148` feeds raw DB cell values into
the curator prompt, whose output becomes `col.description`, rendered verbatim into the
analyst prompt.

### S6. Three security-shaped controls are asserted and absent **[A]**

`design-decisions.md:99-100` (an ADR-grade "Decided" block) and `architecture.md:41` both

- **RLS / tenant isolation:** `Gateway.execute` (`gateway.py:51-70`) takes `identity` and

- **Identity tool-scoping:** `analyst.md:89` and D16 claim `wrap_model_call` *"scopes tools

- **L5 "cost/EXPLAIN"** is a structural cross-join guard only; `guardrails.py:563` says

A reader counting controls gets six or seven; four and a half exist.

### S7. Other security findings **[A]**

- **No forced LIMIT** anywhere in `gateway/`, contradicting `gateway/__init__.py:3` and
  `architecture.md:38`. The cap is `fetchmany(max_rows + 1)` — psycopg's default cursor is
  client-side, so libpq buffers the *entire* result before `execute()` returns.
  `SELECT id, amount FROM huge_table` passes all five layers and OOMs the app.
- **Client-chosen `thread_id` keys a process-global checkpointer** (`graph_app.py:117,131`),

  victim's paused clarification request — which embeds their question — and can resume their
  agent.
- **Langfuse's "mask" is a length truncator, not a redactor.** `obs.py:61-91` truncates

- **The conversation checkpointer bypasses all four run-log privacy gates**

- **The presenter redacts ledger `rows` only** (`presenter.py:812-834`). `entry["reason"]` —
  which for `verdict:"error"` is raw `str(err)`, and libpq embeds `LINE 1: SELECT ...` — ships

  *precisely because* it echoes literals and PII; the externally-reachable surface uses the
  weaker policy.
- **Hardcoded credential:** `run_datalake.py:4440` defaults to
  `"host=127.0.0.1 port=5435 dbname=bird user=bird password=bird"`.
- **Live sample values are committed to git** — `corpus/beer_factory/tables/tbl_beer_factory_customers.yaml`
  already contains `["Kenneth"]`, `["Walton"]`. `profile_database` runs
  `SELECT <col> FROM <table> LIMIT 5` for **every column of every table** with no PII control
  and no pre-sampling exclusion mechanism, then those values go into git, into the LLM prompt,
  into the trace, and out over `GET /schema`.

## Part 4 — Serve-path correctness

The exception-handler discipline here is unusually good — of 63 broad handlers in `src/`,
most are correct or cosmetic. Two are load-bearing.

### R1. The answer is the *last passing* `run_query`, not the agent's conclusion **[V]**

```python
# analyst/agent.py:261-268
def extract_final_sql(final, *, corpus, dialect, default_schema=None):
    """Last passing ``run_query``: sql, tables_used from SQL parse (G3), ledger entry."""
```

It scans the ledger in reverse for the last passing `run_query` and treats that SQL and that
result grid as the answer. The final `AIMessage` content is **never read** for this purpose.
`RUN_QUERY_CAP = 3` permits three passing queries per turn, and nothing marks one as "the
answer."

**Concrete failure [A]:** the model computes revenue with query A (`SELECT SUM(amount)` →
48210), then runs a sanity check B (`SELECT COUNT(*) FROM transaction` → 1204) before writing
its conclusion. Both pass. The user is told "There are 1,204 transactions" for a question
about total revenue. `attempts=2` does push the stamp to `heuristic`, but that is not a
warning a reader parses as "this may answer a different question."

### R2. A crash is served as "outside the governed semantic layer" **[A]**

`agent.py:1007-1023` converts every non-`GovernanceHardStop`, non-`GraphRecursionError`
exception into a refusal reading *"This question is outside the governed semantic layer.
Contact the data owner to add coverage."*

`tools.py:188-200` documents this having already shipped once: a missing `re` import produced
a `NameError` out of every notes tool, *"which the rails then report as an unremarkable
`model_error` refusal."* The import was fixed; the reporting was not. A provider 500, a
`TypeError` from a LangChain bump, and a genuine coverage gap are indistinguishable to the
user, and all three tell them to file a curation ticket.

### R3. REST `/chat` collapses every turn of a session into one audit row **[V]**

`turn_id` is `f"{thread_id}:{n_human}"`. `api/graph_app.py:159` computes and passes the real
human-turn count. **`api/app.py:444` does not** — it omits `n_human=` entirely, and the
default is `1` (`agent.py:1235`).

`_upsert_sqlite` writes `ON CONFLICT(turn_id) DO UPDATE SET payload = excluded.payload`. On
the REST surface, turn 5 of a session **overwrites** turns 1–4. The durable audit record for
a conversation is exactly one row, the last one, silently.

### R4. Audit coverage is best-effort, and there are three ways to execute without a ledger entry **[V]**

Four documents make the absolute claim — `analyst.md:88`, `architecture.md:139`,
`design-decisions.md:374`, `adr/0002:168`: *"You can never execute (or refuse) without a
record."*

1. `append_run_record` is documented **"Never raises"** (`run_log.py:486`) and swallows
   everything into `logger.exception(... non-fatal)` — into a logger with no configured
   handler. The answer ships; the audit row silently does not.
2. **Cache hits** call `gateway.execute()` directly (`governance.py:633`), outside
   `wrap_tool_call`. The returned provenance contains no `governance_ledger` key at all.
3. **Graded delivery** executes outside the middleware (`governance.py:730`).
4. Plus S3: a `RecursionError` in `check()` aborts before the ledger dicts are built.

Additionally, `middleware.py:285-286` excludes `search_corpus`/`inspect_schema`/`read_notes`/
`grep_notes` from the ledger, while `analyst.md:88` promises it records *"each exploration's
surfaced / `excluded`-filtered assets and licensing deltas."* It records a call tally.

### R5. Admitted fail-open inside the fail-closed system **[V]**

`middleware.py:490-493`, verbatim:

```python
# Best-effort and correctness-neutral: a parse/plan hiccup must never turn a
# governed answer into an error, so any failure here yields "no missing edge"
# (the query has already passed check()). Fail-open is safe because a genuine
# cross-schema-without-curated-join case is what this catches, not a leak.
```

The justification does not hold for *this* control: `check()` is precisely the thing that does
**not** enforce D15 — which is why the re-check exists (`middleware.py:163-168` says so). A
`None` return means the `GovernanceHardStop` at `:403` never fires.

Two more in the same file: `:318-319` `except Exception: sql = raw` — normalization silently
skipped on parse failure, and the un-normalized string is what L3 inspects and what executes.
`:186-188` `except Exception: pass` around `model.bind(parallel_tool_calls=False)` — the
sequential-tool-call invariant degrades silently.

### R6. The whole graph is rebuilt per question on the API path **[A]**

`build_serve_rails` carries comments asserting the opposite — `agent.py:353`: schema vectors
are embedded *"once here rather than re-embedding every schema doc on each question."* That
holds only for callers that build the graph once. **Both production callers build a fresh
graph per question** (`api/app.py:444`, `api/graph_app.py:144` → `agent.py:1245`).

Per question on a multi-schema corpus: two full `build_graph(corpus)` projections, two
`column_allowlist(corpus)` builds, a batched embedding call over **every** schema document
(including a `model_copy(deep=True)` of every asset), a fresh empty `RetrievalIndexCache`, and
a new compiled LangGraph. `rvgd.py:281-295` documents that the deep-copy path *"measured 55%
of the serve path's entire non-model CPU cost."* On the API path that optimization does not
apply, and embedding-provider calls scale with `n_users × n_assets` per turn.

### R7. Cache correctness — latent, but the docstring asserts a control that does not exist **[A]**

`SqlCache` is **not wired by any production caller** (verified: no `cache=` at `app.py:444`,
`graph_app.py:145`, or `arms.py:402`), so this is dormant. But the key is the question
embedding and nothing else — no corpus hash, no schema, no dialect, no prompt variant, no
model, no identity. Reviewer probe with the shipped `HashingEmbedder`:

```
0.9444  "...spent more than 100 dollars"  vs  "...more than 200 dollars"  -> HIT (gate 0.92)
0.9375  "...northern region..."           vs  "...southern region..."     -> HIT
```

The rows are re-executed for freshness — for the wrong predicate. And `cache.py:8-11` claims
*"D7 identity scoping means a hit never serves another user's rows"*; `Gateway.execute`
ignores `identity` entirely.

### R8. Other correctness findings **[A]**

- **`must_honour` notes can be budgeted out of the prompt.** `_precedence_key`
  (`note_inject.py:158`) sorts by publication status **first**, normative force second — so a
  `certified`+`advisory` note outranks a `draft`+`must_honour` one. With a 2000-char budget,
  the must-honour rules are what get dropped, and nothing flags it at serve time.
- **Physical-name collisions across schemas mis-ground few-shots.** `rvgd.py:454` keys
  `phys_to_table` on the **bare** physical name, last-write-wins. In a pooled lake, `users`
  from schema B can be licensed for a question routed to schema A.
- **No wall-clock or token bound on a turn** — only a 40-step recursion cap and a 3-query cap.
  Hitting `RUN_QUERY_CAP` returns a ToolMessage and the loop *continues*, burning model
  round-trips until the recursion limit stops it.
- **Embedding degradation to BM25 is invisible in the record** (`schema_router.py:230-243`),
  and its docstring measures the gap precisely: recall@3 0.70 → 0.35.
- **Stale router token usage is folded into the wrong turn** — the narrate node resets
  `last_usage_metadata` and has a regression test; the router path has the same shape and no
  reset, so on the eval path a run of proxy timeouts re-bills the last successful call once
  per question.
- **`stack.narrator` is a process-wide shared mutable** — two concurrent turns cross-attribute
  tokens.
- **`RetrievalResult.scores` are RRF scores** documented and displayed to the model as BM25.

- **`Outcome` forks at the durable run log [V].** `stages.Outcome` members are
  `answered/refused/clarification/capped/crashed`. The `outcome` column is written with
  `"finalize"` (`run_log.py:919` — that's a `Stage`), `"refuse"` (`:917`, `agent.py:484` — the
  member is `refused`), and `"ok"`/`"error"` (`curator/pipeline.py:353`, `sme.py:342`).
  `classify_row` does `Outcome(str(stamped))`, so every durable row raises `ValueError` and
  silently falls back to re-derivation. `docs/measurement.md:769` tells operators to read that
  column to distinguish `crashed` from `refused` — it can never hold either value.
- **13 hardcoded, mutually inconsistent SQL dialect literals.** `api/stack.py:229` threads
  `datasource.kind` correctly; thirteen sites ignore it. `eval/oracle.py:149` hardcodes
  `"postgres"` while `eval/retrieval_eval.py:58` hardcodes `"sqlite"` — **the same gold SQL is
  parsed under two grammars**, so recall@K and the error taxonomy are computed over
  differently-parsed table sets.
- **OpenAI price table past the LLM seam.** `llm/client.py:22` claims nothing outside imports
  `openai` — verified true. But `run_log.py:82-89` hardcodes six OpenAI SKUs, so a Bedrock
  deployment silently reports `cost_est_usd = None` on 100% of turns while `adr/0004:148`
  lists cost as a guaranteed Tier-A field.
- **Three curator prompts bypass the registry** (`llm_proposer.py:33-58`, `sme.py:54-56`,
  `sme.py:294-298`). `registry.py:1` claims to hold *"every prompt this system sends."*
  `LlmProposer` is what distinguishes `curated` from `seeded` — editing its prompt changes
  every curated corpus and therefore EX, while `prompt_set_hash` stays byte-identical. That is
  verbatim the failure `registry.py:9-13` claims to have closed.
- **`Answer.provenance` is an untyped `dict`** on an otherwise fully-typed frozen dataclass,
  in a repo with 25+ strict pydantic models. **93 `.get()` reads across ~40 keys**, and it is
  the public wire type. The repo already compensates with a hand-maintained key tuple —
  which `registry.py:19-20` mocks as *"the exact trap `serve_config_hash`'s hand-maintained
  field list fell into."*
- **`Stage` enum declared, raw strings used.** `agent.py:1203` uses both vocabularies on one
  line: `builder.add_node("cache", _timed(Stage.cache, cache_lookup))`.
- **`viz` reimplements graph BFS and SQL join parsing** that `graph/planner.py` and
  `corpus/validate.py` already own, with the weaker implementation.
- **Import cycles:** `corpus ↔ gateway` and `curator ↔ eval` (both TYPE_CHECKING-guarded, so
  benign) plus genuine module-level cycles inside `retrieval/` held apart by 8 lazy imports.
  **120 function-local internal imports** and **40 cross-module private imports** are the
  load-bearing structure keeping the graph acyclic.

### Config **[A]**

65 settings across 4 dataclasses. **~16 of 65 (25%) carry no runtime behaviour**: 7 fields
have zero readers anywhere, plus the `MemoryBudget` class and `ROUTE_MEMORY_BUDGETS` constant;
**9 more are read only by the provenance hash** — editing them invalidates run comparability
while changing nothing. `auto_accept_corpus` is the sharpest: the D6 human gate is
fingerprinted but never enforced.

**Every table except `[prompts]` accepts typos and wrong types silently [A]:**

| TOML input | Result |
|---|---|
| `[models] llm_modle = "x"` | dropped; default silently retained |
| `[models] max_retries = "two"` | passed straight into `ChatOpenAI(max_retries='two')` |
| `[logging] run_log_kind = "none"` | **falls through to sqlite** — you believe logging is off, it is writing |
| `[serve] allow_edt = false` | dropped; the corpus-write endpoint stays open |

`config.py:585-594` shows the right pattern applied to exactly one table, with the rationale
stated: *"a typo fails at startup instead of silently serving v1."*

Also: `_compute_repo_root` breaks for any wheel install (falls back to `<venv>/lib`, so every
relative path silently becomes meaningless); `.env` is loaded as an **import-time side effect**

**Dependency floors are fiction.** `uv.lock` resolves `openai` **2.44.0** against a
`>=1.40` floor, and `sqlglot` **30.12.0** against `>=25.0` — five majors below what 30 call
sites were written against, on the library the L3 guardrail depends on. `uv sync` is safe;
`pip install governed-bi` is not.

## Part 8 — What actually holds up

Worth stating plainly, because it is real and the report above is relentless.

- **The guardrails are a competent SQL-shape filter.** Every injection shape probed was
  blocked at the correct layer, including DML hidden in CTEs, function denylist evasion
  through schema qualifiers, comment obfuscation, and homoglyphs. Unparseable input and an
  empty allowlist both fail **closed**.
- **SQLite read-only is genuinely enforced** and genuinely tested with a real `pytest.raises`.
- **`SET statement_timeout` is real and server-side.**
- **Path traversal in `/corpus/edit` is fixed three layers deep**, with the
  `\A...\Z`-not-`$` reasoning explicitly documented.
- **No `eval`/`exec`/`pickle`/`shell=True`/unsafe `yaml.load` anywhere.** The YAML loader is
  a `SafeLoader` subclass.
- **API keys and DSNs are env-var-*name*-only in config**; the missing-DSN error names the
  variable, not the value; manifest writing strips credentials from DSNs deliberately.
- **The EX denominator is right.** A refuse-everything arm scores 0.0, not 1.0.
- **Arm isolation is tight** — only `corpus=` differs across arms.
- **`treatment.py` is the best idea in the harness** — it catches the "corpus built, never
  injected" failure this project actually hit twice, and no reviewer could construct a pair
  that evades it.
- **The statistics are correct where they exist:** exact binomial McNemar, Holm over the right
  family with replicate pairs excluded, CIs on the per-question unit, duplicate ids fatal.
- **`oracle_sql` measuring the grader's own ceiling** is an instrument most harnesses lack.
- **The test suite is green, fast (10s), offline, and genuinely order-independent** across
  multiple seeds — real hygiene, not luck.
- **CI asserts the demo database exists** rather than letting integration tests silently
  mass-skip, and uses `-rs` to surface skip reasons.
- **`stages.py`, `prompts/registry.py`, and `validate.py`'s leakage disclaimer are unusually
  honest engineering** — several findings in this report are things the codebase already says
  about itself.
- **`stack.py:209` fails loud** rather than silently serving all-access.
- **EN/zh doc pairs have not drifted**, and there are zero dead doc links.

## Appendix — method

Seven reviewers ran concurrently with explicit adversarial framing and non-overlapping scopes:
security red-team, eval methodology, architecture, docs-vs-code, serve correctness, test
suite, ops + curator. Each was instructed to anchor every finding to a line it read, to report
concrete failure scenarios rather than generic advice, and to include a section on what it
tried to break and could not. Findings marked **[V]** were then reproduced independently.

Two claims were corrected during the audit: the Postgres connector's read-only enforcement
(initially scored as holding up; it is a no-op) and the eval-driver relationship (framed as a
copy-paste fork; it is a private-API dependency with parallel reimplementations that have
already drifted).

Reproduction commands used for the **[V]** findings:

```bash
uv run pytest -q -p no:randomly
uv run python -m governed_bi.corpus.cli
grep -rn "except Exception\|except BaseException\|except:" src/ | wc -l
```

The working tree is unchanged: `git status --porcelain` is empty. One stray `langgraph dev`
process started by a reviewer was stopped.
