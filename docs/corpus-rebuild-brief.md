# Corpus rebuild brief

For the coding agent that will rewrite `../BIRD-corpus` from nothing.

The corpus in the tree today was generated by several out-of-tree scripts over several
attempts and conforms to almost none of ADR 0005's field spec (measured: 100% of corpus B's
schema, table and column summaries are identifier lists with a function-word ratio of 0.000;
0/928 joins carry a `body`; 46% of terms whose summary must contain their aliases do not).
None of it is worth patching. Delete and rebuild.

**The goal is the best corpus we can write for this database.** Every fact we hold about
`pg_rename_decoy` is fair input, including which columns carry unreliable data. What is *not*
fair input is the held-out split and its answers.

Three phases, in this order:

1. **Delete** everything, on a branch.
2. **Scaffold** deterministically, by standalone script. No model calls.
3. **Populate** the written fields, by agent, one table at a time, behind a validator that
   can reject.

The validator in §5 is written **before** phase 3 starts. Last time there was no validator,
and an agent writing 656 tables with nothing to fail against regressed to templates. That is
the single structural difference between this attempt and the last one.

Everything else in `BIRD-Data-Obfuscation` is in scope, **including

rename+decoy instance; a steward maintaining it would know which of its columns are junk, and
withholding that from the writer produces a worse corpus, not a fairer one. What that knowledge
may be *turned into* is constrained by §4.4, for reasons of retrieval correctness rather than
fairness.

`tools/routing_recall.py` and `tools/query_summary_alignment.py` currently **default to
`test_final.jsonl`**. Repoint them at `train_final.jsonl` before anyone runs them.

**N2 — Do not trust a docstring.** This repo has shipped false ones, and this brief was
rewritten twice because of them. Every claim in §1 was re-read from executing code and carries
a `file:line`. Hold anything you write to the same standard.

**N3 — Nothing ships until the validator passes.** Per file, not per batch.

## 1. The field contract

Verified by reading the implementation, not the comments. **Read this before writing anything**
— three of the four rows are counter-intuitive and every past corpus got at least one wrong.

| field | enters the retrieval index | enters the prompt | can the budget drop it |
|---|---|---|---|
| `summary` | **yes — both channels, and it is the only text that does** (`retrieve/index.py:117-125` builds the BM25 docs from `entry.summary.strip()`; `:151-159` keys every vector on the same string) | **no** (`serve/context.py` never emits it; sole exception is a few-shot with no `body`, `context.py:167-171`, dead on 5000/5000) | — |
| `body` | no | **yes, for a hit only** (`context.py:130-142`) | **yes — first rung of the eviction ladder** (`context.py:313-322`) |
| `rules` (schema only) | no | yes, as `## Must honour` (`context.py:96-98`) | no |
| `reliability.status` + `.note` | no | yes, as `## Reliability caveats` (`context.py:264-285`) | **no** (`_piece` hard-codes `evictable: False`, `context.py:181-182`; the ladder only touches `struct_with_body` and evictable *tables*) |
| structural fields (`physical_name`, `physical_type`, `grain`, `cardinality`, `on`, `expression`, `binding`) | no | always (`context.py:371-433`) | no |

Four consequences to hold in mind while writing:

- **`summary` is retrieval and nothing else.** Prose quality there buys ranking, never answer
  quality. Write it to be *found* — and, for a column that must never be used, write it *not*
  to be found (§4.4).
- **`body` is the whole message to the model, and it is the first thing dropped.** Front-load it.
- **`reliability` is the only field that both reaches the model and cannot be dropped.**
- A blank `summary` is not a soft failure: `build_index` raises (`index.py:118`).

## 3. Phase 2 — the deterministic scaffold — **built**

**Standalone scripts, deliberately outside the package.** One-shot, BIRD-specific, not portable;
not part of `governed_bi`, not imported by anything in `src/`, and not inside `../BIRD-corpus`
(an asset-adjacent file becomes part of `corpus_content_hash`).

```
governed-bi/
  scripts/corpus_rebuild/
    README.md            _common.py
    01_structure.py      02_joins.py        03_few_shots.py
    04_evidence.py       05_bird_docs.py    06_samples.py
    _build/              # staging output, gitignored
```

All six run. Verified against `address` and `airline`: 01–03 produce a tree that **loads
cleanly and fails conformance** — V14/V3/V9/V13 zero, V2 and V6 at 181 — and two runs over the
same inputs are byte-identical.

Plain Python: stdlib + `pyyaml` + `psycopg` + `sqlglot`. No engine imports, **with one
exception**:

```python
from governed_bi.corpus.identity import table_id, derive_column_id, join_id, slug
```

Ids must have exactly one spelling. When they did not, `airline."Air Carriers"` ended up with
no table asset at all while 24 few-shots cited it. Re-deriving that logic in a script is how
you get a second spelling. Import the four functions; write everything else yourself.

Each script is re-runnable and byte-identical from the same inputs.

### 3.1 `01_structure.py` — from the live database

Reads `PG_RENAME_DECOY_DSN` (introspection only).
Writes every `TableAsset` with inline `ColumnAsset`s: `schema`, `physical_name`,
`physical_type`, `nullable`, `is_unique`, derived ids.

`summary` is written as `TODO <identifier>`, `body` left empty. **The sentinel must fail the
validator.** Do not seed a plausible-looking template — the existing corpus is what happens when
an agent finds one already there and leaves it alone. (`corpus/seed.py:54` writes
`f"{schema} — {len(tables)} tables: "`, a roster with a function-word ratio of 0. It is the only
producer in `src/` and it violates the spec it was written for. Do not reuse it.)

The identifier rides along in the sentinel so the floor **loads while failing conformance**. A
bare `TODO` is rejected by the model's own identifier rule, which drowns V14 — the rule that
catches a structurally broken file — in noise from every unwritten asset. *Unfinished* (V2) and
*broken* (V14) have to be different signals; the first version of this script got that wrong and
reported 18 loader failures that were all just unwritten summaries.

### 3.2 `02_joins.py` — from foreign keys and train gold SQL

Reads `data/*/**/*_tables.json` (`foreign_keys`) and `train_final.jsonl` (`sql_rename`, JOIN
clauses only). Writes `JoinAsset` with `left_table`, `right_table`, `on`, `cardinality`.

- `on` **must be schema-qualified** — `address.CBSA.CBSA = address.zip_data.CBSA`. The
  unqualified form is what `corpus-a-20260807` was fixing, and `join_id` embeds `on_digest`, so
  the two forms mint different ids.
- 38 real tables currently carry no edge at all (8 of them in `hockey`). Harvesting JOINs from
  train gold SQL, not just declared foreign keys, is what closes that — there are no FK
  constraints in these instances.
- `summary` = sentinel, `body` = empty. The agent fills both.

### 3.3 `03_few_shots.py` — from train gold SQL

Reads `train_final.jsonl` only. Writes `FewShotAsset`: `sql` verbatim, `summary` = the question
verbatim, `body` = `"Question: …\nSQL: …"`.

**Not an agent job.** Rewriting harvested SQL with a model costs money and invents SQL.

Two filters that were missing last time:

- **Drop any few-shot whose gold SQL reads no table** (`SELECT … FROM (VALUES …)`) —
  transpilation artifacts, not queries; 9.9% of the train split. They are also what produced the
  15 assets over 80 KB, one of them 5.1 MB, together **50.5% of the entire corpus by bytes**.
- **Hard cap 4,000 bytes per asset.** Anything larger is a materialised result set.

### 3.4 `04_evidence.py` — extract clauses, author nothing

Reads `train_final.jsonl` `evidence_rename`. Writes `_build/evidence_clauses.jsonl` — **staging,
not corpus assets**.

Split on `;` and on clause-separating commas. Per clause:

```json
{"db": "address", "clause": "highest average house value refers to Max(avg_house_value)",
 "shape": "metric|term_value|term_column|value_gloss|other",
 "identifiers": ["avg_house_value"], "literals": []}
```

Measured on train: 8,775 distinct clauses over 57 schemas — 1,200 metric-shaped, 2,828
`term = value`, 2,020 phrase→column, 363 value glosses. **97% name at least one real obfuscated
identifier**, so binding is mechanical.

The agent writes terms and metrics from this (§4.3). A clause transcribed verbatim is
benchmark-shaped text, not what a person maintaining a warehouse would write.

### 3.5 `05_bird_docs.py` — stage BIRD's own documentation

Reads `data/*/**/database_description/*.csv`, `*_tables.json`, `schema_rename_map.json`.
Writes `_build/bird_docs.jsonl`, one row per obfuscated column:

```json
{"db":"card_games","table":"cards","column":"availability","original":"availability",
 "nl_name":"","description":"A list of the card's available printing types.",
 "data_format":"text","value_description":"\"arena\", \"dreamcast\", \"mtgo\", \"paper\""}
```

Encoding: a mix of UTF-8 and cp1252. Try `utf-8-sig`, then `cp1252`, then `latin-1`; never
silently skip a file.

**Set expectations honestly.** 515 CSVs, 3,663 rows, 2,542 distinct `(db, column)` pairs against
4,596 real columns. `column_description` is present on 91.5% of the rows it covers, but its
**median length is 28 characters** and 9% merely restate the column name ("the title of the
movie", "the name of the medal"). `value_description` covers 27.4%.

A starting point, not a description. The agent writes; it does not transcribe.

### 3.6 `06_samples.py` — from the live database

Per column: `SELECT DISTINCT … LIMIT 5`, plus min/max for numerics and dates. Writes
`_build/samples.jsonl`. Read-only, against `pg_rename_decoy` — the instance the eval grades on.

For a column named in `trap_manifest.json`, still sample it: the writer needs to see that the
values *look* plausible, which is the whole difficulty.

## 4. Phase 3 — the agent pass

### 4.1 Unit of work: one table

One call produces the `TableAsset` **and every one of its inline columns** — summary and body
for each. Not one call per column.

A column's description depends on its siblings and its table (the spec asks for "how it differs
from its siblings"); columns are stored inline anyway; and it is 656 calls instead of 6,603.

Then a smaller pass for the 57 `SchemaAsset`s, which needs the finished tables as input, and a
third for joins, terms and metrics.

**One schema at a time, start to finish, one commit per schema.** A bad schema is redone without
touching the other 56.

### 4.2 What the agent is given, per table

- the structural scaffold from §3.1 — identifiers, types, nullability
- its rows from `_build/bird_docs.jsonl` (§3.5)
- its rows from `_build/samples.jsonl` (§3.6)
- this schema's clauses from `_build/evidence_clauses.jsonl` (§3.4)
- **the trap manifests** — which of this table's columns carry unreliable data, and whether this
  whole table is an unreliable clone
- the other table names in the schema, and the join edges touching this one

Not given: the test split, gold answers, paraphrases.

### 4.3 Per-field rules

**`summary` — what the thing IS, written to be found.**

- A full English sentence or a clean noun phrase. Not a roster, not a template, not
  `name — table.name`.
- Contains the asset's own physical identifier, **bare**. ADR 0005 §1.1 and §1.2 disagree here —
  §1.1 says bare `physical_name`, §1.2 says `table.column`. **§1.1 wins**: qualification spends
  the character budget on what the tag rule already establishes, and a `(column zip_code)`
  suffix — which 69% of `corpus-a-20260807` carries — is a template tail, not a sentence.
- **No values, no examples, no `e.g.`, no quoted literals.** Those are `body`'s job by spec, and
  15% of `corpus-a-20260807`'s table and column summaries break this.
- ≤ 250 characters for table, column, join, metric, few_shot. **≤ 400 for `SchemaAsset`** — the
  only place the cap measurably binds (mean summary length on `corpus-a-20260807`: 220.8 for
  schemas, 154.4 tables, 99.8 columns). 400 is provisional; §6 measures it.
- A `TermAsset`'s summary contains **every one of its `synonyms`**, verbatim. Only `summary` is
  indexed, so an alias living anywhere else is unreachable. Broken today on 441 of 949.

**`body` — everything the model needs, self-contained.**

The model never sees `summary`. A `body` that assumes the summary was read is a bug.

- `SchemaAsset`: business background, cross-table conventions.
- `TableAsset`: what it is, grain, time coverage, which table it is confused with.
- `ColumnAsset`: **the value domain** — code table, units, format, how it differs from its
  siblings. Where `value_description` and the sampled values go. Today 42% of column bodies are
  the tautology `Means 'X' (obfuscated to 'X')`; that string is banned.
- `JoinAsset`: when to take this edge rather than another, fan-out risk. **0 of 928 have one.**
- `TermAsset` / `MetricAsset`: full definition, boundary conditions.

**`rules` (schema only)** — hard constraints that hold every turn. Few and load-bearing; they
render as `## Must honour` and are never dropped. Not a place for descriptions.

**`TermAsset` and `MetricAsset` — deduce, do not transcribe.**

The evidence clauses are raw material:

- Several clauses often describe one concept in different words. Merge them into **one** term
  whose `synonyms` carry every phrasing seen.
- `above-average female population refers to female_population > DIVIDE(SUM(female_population), COUNT(...))`
  is a metric definition wearing a filter's clothes. Extract the metric (`AVG(female_population)`);
  put the comparison in `body` as a boundary condition.
- Never copy a clause verbatim into a `summary`. Write the definition a data steward would write,
  in the vocabulary a user would say.
- Bind every term (`binding.target_id`) and metric (`base_table`, `expression`) to a real asset
  id. An unbound term is untagged and casts no vote in routing.

Coverage today: 6,048 harvestable clauses produced 1,393 assets — 23%, and 10–16% on the worst
schemas. Aim higher, but **more is not automatically better**: the facet budgets are `term=5` and
`metric=5` per turn, so near-duplicates crowd each other out. Deduplicate aggressively.

### 4.4 Unreliable columns and tables

The agent knows which columns and tables carry corrupted data. Three rules govern what it does
with that, and only the first is about disclosure.

**Rule 1 — say it is unreliable, not why.** Write, on every affected column:

```yaml
reliability:
  status: suspect
  note: "Unreliable for analysis. Do not use this column to answer questions."
```

No `decoy`, `trap`, `fabricated`, `synthetic`, `planted`, `imitates`, `mimics`. The note is the
same sentence everywhere; it carries no per-column information. `reliability` is the right home
because it renders in its own block (`context.py:264-285`), it is `evictable: False` and the
eviction ladder cannot reach it (`context.py:181-182`, `:313-336`), and it does **not** enter the
retrieval index.

**Rule 2 — never name the column it resembles, anywhere.** This is a retrieval defect, not a
disclosure one. `summary` is the index. The current corpus writes *"Fabricated to mimic
'zip_code'"*; put anything like that in `summary` and the unreliable column starts ranking for
every zip-code question, competing with the real one for the same 30-column budget. The corpus
puts it in `body` today, which is survivable only because `body` is not indexed — and the
"index more fields" change under consideration in §7 would break exactly that.

**Rule 3 — an unreliable column's `summary` is identifier-anchored and semantically thin.**

It must be non-blank (`index.py:118` raises) and must contain its physical name, so the model can
spell it and the caveat block can name it. It must **not** be written to win retrieval. Say what
the column is called and what type it holds; do not give it the domain vocabulary that would make
it a good match for a real question.

```yaml
# real column
summary: The alternate place or city name recorded for a ZIP code's postal area (alias).
body: One alias per zip_code, e.g. 'Amherst', 'URB San Joaquin'. Join to zip_data on zip_code.

# unreliable column, same table
summary: alt_alias, a text column on the alias table.
body: >
  Values in this column are not dependable and do not correspond to the business facts the
  table otherwise records. It must not be used in a SELECT list, a filter or a join key.
reliability:
  status: suspect
  note: "Unreliable for analysis. Do not use this column to answer questions."
```

For an unreliable **table** (141 of them), the same shape at table level, and every one of its
columns carries the caveat too.

For an unreliable column whose manifest entry says `is_key: true` (748 of 1,486), add one clause
to `body`: it must not be used as a join key. That is a fact about the data, not about how it
was made.

> **One measurement consequence, stated once and then dropped.** Because the flags come from the
> manifest, an arm built on this corpus measures *"does a governed layer that knows which columns
> are junk help?"* — a real product question; a real steward does know. It does not measure
> whether the system can *detect* junk. If that second question ever matters, the arm for it is
> this same corpus with the `reliability` blocks stripped, which is a one-line filter.

## 5. The validator — **built**

`tools/check_corpus_conformance.py`. It lives with the other gates rather than in
`scripts/corpus_rebuild/` because it outlives the rebuild: any corpus, any time.

```bash
# the rebuild loop, after every file the agent writes
uv run python tools/check_corpus_conformance.py --file <path>

# the whole tree, with a per-rule report
uv run python tools/check_corpus_conformance.py --corpus-dir ../BIRD-corpus
```

Exit 1 on any violation. Rules that need the whole tree or an external manifest report
**not evaluated** rather than passing, because a rule that silently skips reads exactly like a
rule that passed.

Counts below are what it reports today, so they are the debt the rebuild clears:

| # | rule | corpus B (`main`) | corpus A |
|---|---|---:|---:|
| V0 | the file parses and declares a known `asset_type` | 0 | 0 |
| V1 | `1 ≤ len(summary) ≤ cap` (400 schema, else 250) | 0 | 0 |
| V2 | `summary` is not the scaffold sentinel | 0 | 0 |
| V3 | `summary` carries the identifier `ASSET_REGISTER` declares | 0 | 0 |
| V4 | `summary` is prose: function-word ratio ≥ 0.10 **and** no template shape | **7,046** | 892 |
| V5 | no values, examples or `(column x)` tail in `summary` | 542 | **6,005** |
| V6 | a type whose spec names a `body` has a non-empty one | **2,068** | 1,955 |
| V7 | a column `body` is not a tautology | 2,520 | 2,520 |
| V8 | a term's `summary` carries every one of its `synonyms` | 558 | 558 |
| V9 | every declared reference resolves to a real asset | 0 | 0 |
| V10 | no text discloses how an unreliable column was made | 2,442 | 2,443 |
| V11 | a suspect column's `summary` omits the column it resembles | 13 | **333** |
| V12 | no asset quotes a held-out question | 0 | 0 |
| V13 | no file over its cap (few_shot 4 KB, else 32 KB) | 53 | 54 |
| V14 | **the engine's loader accepts the file** | 0 | 0 |

Two of these deserve a word.

**V11 caught what §4.4 rule 2 exists to prevent, and only after a bug fix.** It first reported
0 on both corpora, because it keyed on `(schema, physical_name)` while an inline column carries
no `schema` of its own — the loader derives it. Vacuous, and indistinguishable from clean. With
the fix it finds **333 summaries in corpus A that name the column their unreliable column
resembles**, which is the retrieval defect: those 333 now rank for the real column's questions.

**V14 exists because the text rules cannot see a structural break.** The first scaffold wrote
`provenance.source: introspection`, which is not one of the four values the enum allows. Every
text rule passed; the loader returned zero assets from 18 files. A validator that green-lights a
file the engine rejects is the vacuous-gate problem one level up.

**V5 does not apply to a few-shot.** Its `summary` *is* the question by spec, and questions
legitimately quote the values they ask about — policing value-talk there would reject §1.2.

**V5 and V4 trade off, which is the shape of the whole problem.** Corpus A fixed the templates
(V4 7,046 → 892) by moving prose into `summary`, and in doing so pushed values and examples in
with it (V5 542 → 6,005). Both fields were being asked to do one job. The rebuild does not get
to make that trade: §4.3 splits them.

V4's threshold and V10's word list are the two an agent will argue with. Change them in the
validator, with a measurement, or not at all.

Every rule has a test that proves it fires
(`tests/conformance/test_corpus_conformance_rules_fire.py`, 20 cases), and the suite asserts
that no rule is added without one — a rule nobody provoked is the V11 failure again.

## 6. Measure where you landed

No pilot gate — the defects are understood and the rebuild proceeds straight through. But run
this once the rebuild is done, because it is free and it is the only thing that tells you what
the rewrite bought:

```bash
uv run python tools/routing_recall.py --corpus-dir ../BIRD-corpus \
  --baseline <path-to-old-corpus> --no-rewrite --top-n 3
```

No model calls, and the 365 MB vector cache under `runs/vectors` is already warm. It reports
`recall@{1,3,5,10}` and table coverage for both corpora in one process, same embedder, same
questions — the only way the two numbers are comparable.

Read it as a diagnostic, not a verdict. The old corpus was tuned on the test split
(`tools/densify_summaries.py`'s acceptance bar was +6.1pp measured on `test_final.jsonl`), so it
is not a fair target; and that +6.1pp was measured while the semantic channel was dead on every
turn, so the whole "richer indexed text helps" result is lexical-only evidence awaiting a re-run.

Sweep `--top-n 3/5/10` in the same pass. It costs nothing and settles the 400-character schema
cap in §4.3 at the same time.

## 7. Out of scope, deliberately

- **The engine indexes `summary` alone.** A schema's `body` and `rules` — its real domain prose —
  never enter retrieval. That is an engine change, free to test, and it may matter more than any
  corpus rewrite. Do not pre-empt it by stuffing `summary`.
- **`_visible()` now honours `governance.excluded` in the index** (`serve/session.py`), so
  withholding an unreliable column entirely — rather than describing it and warning — is a
  one-field flip. This brief describes and warns; the flip is available later.
- **Reproducibility.** Phases 1 and 2 are reproducible; the agent pass is not. Record the inputs
  instead — `Provenance.source_refs`, `version`, `model` — so a re-run is auditable even when it
  is not byte-identical.
