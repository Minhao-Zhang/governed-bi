# Pivot: a plain chat app that answers, and nothing around it

Status: proposed, 2026-10-19. The decisions are recorded in ADRs 0017 to 0020. This memo gives
the reasons behind them and the order of work. It replaces the
[trim plan](2026-10-trim-plan.md), its [milestones](2026-10-trim-milestones.md) and the
[Ossie plan](2026-10-ossie-plan.md).

## 1. The short version

governed-bi becomes what it set out to be: an engine that answers questions about a database with
the SQL behind the answer, or refuses, or asks. It is served as one plain chat page. Every answer
says what it assumed, and the server checks those assumptions against the SQL. The semantic layer
is something the user brings. Its Ossie export can be opened in a separate viewer, which is its
own project. Everything else goes: the access policy, the feedback product, the extra pages, and
most of the checks the repository runs on itself.

By a rough count, the Python source falls from about 43,000 lines to about 29,000, the UI from
21,500 lines to a few thousand, and the tools from 40 files to about 10.

## 2. What we set out to do

The first commit (`7627eb2`, 2026-07-08) described "natural-language questions → grounded,
governed, auditable answers over relational data". The engine would fail closed, answering with a
refusal or a clarifying question rather than a confident wrong number. Identity, row-level security
and scoped memory were "seamed in but toggled off". The README still opens with the same promise:
"Get an answer, the SQL behind it, or a reason it could not answer."

That design also had a curator that wrote the semantic layer. It was deleted with v1 on 2026-08-02
and never redesigned, and it stays out. Building the layer is a different product.

## 3. How we drifted

After the v1 delete, the work went into the serving side, which was right, and then into things
around it, which was not. August added an access policy that has never held more than one
principal and a feedback product whose only reader was the owner. It also added a layer of checks
on the repository: a register of 63 declared knobs, 22 corpus conformance rules, 84 code mutations
run nightly, 12 `check_*` gates, a parcel map of the tests, and quotability gates on every number.
Retrieval, the core of the engine, is 2,441 lines out of 42,907, and the tests are 52,000 lines,
more than the code they test.

The UI grew the same way, to eight pages with display levels for engineers and analysts. Ten
redesigns drafted on 2026-10-19 added still more interface, and all ten were rejected for it.

The trim plan set out to cut the two subsystems with no users, but would have left the machinery
that makes every deletion cost six PRs and a second reviewer.

## 4. The decisions

| ADR | Decision |
|---|---|
| [0017](../adr/0017-a-served-chat-app-over-a-layer-the-user-brings.md) | What the project is, what stays, what goes, and how the deletions are shown to be safe |
| [0018](../adr/0018-every-answer-states-its-assumptions.md) | Every answer lists its assumptions, each marked as backed by the layer, a convention or a guess. The server checks them against the SQL, and a guess between two definitions becomes a clarifying question |

## 5. Order of work

In governed-bi, each step one or a few PRs:

1. **Accept the ADRs.** Update `AGENTS.md` to point here, which needs the owner's consent.
2. **Take the offline snapshot** described in 0017 §4, and confirm two runs match byte for byte.
3. **Delete** what 0017 §3 lists, in a few large PRs, each one matched against the snapshot.
   Rewrite ADRs 0009, 0012, 0015 and 0016 as reversal records as their code goes.
4. **Rename to plain words** as §6 describes, code and docs in the same PRs, each matched
   against the snapshot.
5. **Add assumptions** to the answer tool, the server's check against the parsed SQL, and the
   guess count to the abstention policy (0018).
6. **Rebuild the UI** as 0019 describes, with its tests.
7. **Write the Ossie exporter** and its validation test (0020).
8. **Measure** with the chosen model setup, twice on all 1,351 questions, and record the
   baseline for the `dev` half, the `holdout` half and the total.
9. **Rewrite the README and `docs/`** for what is left.

In the new viewer repository, which can start at once:

1. Load and validate a file, and draw the dataset graph.
2. Add the field, metric, `ai_context` and extension views, then links that open on one item.
3. Test it on `../ossie/examples` and on the exported BIRD layer.

## 6. Plain names

The code and docs use words the project made up for things that already have ordinary names. A
reader has to learn "a five-facet retrieval", "a paired arm", "the licensed set" and "a knob"
before reading anything else, and some of these words mislead. "Licensed" sounds like a
permission, and the glossary has to say that it is not one. Most of them come from AI-written
text, and Claude in particular keeps reusing words like "load-bearing" and "seam" even when told
not to ([claude-code#53454](https://github.com/anthropics/claude-code/issues/53454)). So the
rename needs a check in CI, not only a rule in `AGENTS.md`.

### 6.1 The renames

These stay, because they are standard terms: principal and grant until 0017 deletes them, channel
as LangGraph's own word, corpus, coverage, artifact, and the paired test. Words that go with the
code 0017 deletes need no rename: return path, observation, patch, derived state, cluster,
ratchet, conformance, mutation.

These go from prose everywhere, with nothing in their place: actually, genuinely, quietly,
honest or honestly as emphasis, load-bearing, theatre, spine, "worth naming", "the part worth".

### 6.2 How

- **Rewrite sentences, not words.** "One paired `--abstain` arm" becomes "one run with
  abstention on, compared with one run with it off". Swapping word for word leaves
  "one side-by-side `--abstain` configuration", which is new jargon.
- **Code and docs in one PR per group of rows**, so the docs never describe names the code no
  longer has. Old names get no aliases, except where noted below.
- **After the deletions and before the baseline run.** After step 3 there is a third less code
  to rename. Before step 8, because renaming a setting changes the config hash, and step 8 is the
  first run that has to be compared with later ones. No run before it is compared after it, so
  the hash change costs nothing.
- **Before the UI rebuild and the assumptions work**, so the new code is written with the new
  names. The HTTP fields that change (`licensed`, `knob`, `gate`, `stamp` and others in
  `docs/openapi.json`) change in the same PR as the UI that reads them.
- **The snapshot changes its field names, not its values.** Each rename PR lists the renamed
  snapshot fields before the run, and the values must still match exactly.
- **Old files stay as they are.** Files under `runs/` and accepted ADRs keep the words they were
  written with, because they record what happened. A note at the top of `docs/glossary.md` maps
  the old names to the new ones so those files stay readable.
- **A check keeps the words out.** A small `tools/check_plain_names.py` reads the table above from
  one file and fails CI when a replaced word appears in Markdown or in a Python or TypeScript
  comment, docstring or identifier. It skips `runs/`, accepted ADRs and the glossary's mapping
  note. This is the one repository check this plan adds, and it is short.
- **`AGENTS.md` gets one rule pointing at the table**, with the owner's consent, as step 1 needs.

## 7. Questions the owner has answered

All decided on 2026-10-19; the full list of decisions is section 7 of the
[milestones](2026-10-pivot-milestones.md).

1. **The first user** is the owner, on BIRD-corpus. There is no pilot yet, so the plan covers no
   second user's access or data.
2. **The model setup** is OpenAI only: `gpt-6-luna` for both the agent and the utility model, and
   `text-embedding-3-large` for embeddings.
3. **The viewer** is `ossie-viewer`, a public repository under the owner's GitHub account, to be
   offered to the Ossie project once it is useful.
4. **The DetentAI fork's PR #3** is closed with thanks, and ADR 0018 cites its finding that the
   `assumptions` field was never filled.
