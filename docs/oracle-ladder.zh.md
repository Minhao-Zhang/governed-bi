# oracle 阶梯：一个阶段的失败到底值多少

_对应英文文档：[oracle-ladder.md](oracle-ladder.md)（该文档目前没有语言切换行，此处仅作对应标注）_

[错误分类体系](measurement.zh.md#错误分类体系按阶段与按类别)说的是错误答案
*从哪里*来。它说不出修好一个阶段能换回多少，而那种看起来能给出答案的
算法——把按类别的计数直接加总——是错的。在上一次基准测试里，61% 的错误
答案同时在不止一个维度上出错，所以"203 个问题选错了表"并不是 203 个可以
救回来的问题：把表修好之后，这些查询里的大多数在别的地方仍然是错的。把
按类别的计数直接加总，会对每一条多类别的查询重复计数，而这正是某份报告
最初得出"还有 46 个百分点可以拿"、后来又改成"3–5 个百分点"，中间却没有
任何东西能证明这两个数字里哪一个成立的原因。

`src/governed_bi/eval/oracle.py` 直接回答这个问题，而不是去估计它。把
gold 答案交给某一个阶段，其余阶段原封不动，让问题重新走一遍普通的
agentic core，再去测量。EX 的差值*就是*那个阶段的可提升空间，交互效应
已经包含在里面，因为流水线剩下的部分仍然要完成自己的工作。

## 四档

`OracleRung` 有四个成员，成本递增，真实度递减：

- **`oracle_sql`**——跳过模型，把 gold SQL 直接交给评分器。不花任何成本，
  回答的是一个此前没人问过的问题：*评分器*给 gold 打出的分数是多少？只要
  低于 1.0，就是一个评分缺口——一个冻结常量、一个过期的 hash、一个
  归一化上的怪癖——它才是其余所有数字应该拿去对照的真实上限。先跑这一档：
  一个 0.81 的上限，会让 0.44 的 EX 读出来和拿一个假定的 1.0 去对照时
  截然不同。
- **`oracle_schema`**——把 corpus 钉死在 gold schema 上，这样路由就不可能
  选错。相对公平阶梯的 EX 增益，就是 schema 路由的全部代价，包括那部分
  会渗透进 SQL 生成阶段的代价——模型在错的表上，也能写出看起来挺像那么
  回事的 SQL。
- **`oracle_tables`**——把 corpus 进一步收窄，只留下 gold 实际用到的那些
  表。相对 `oracle_schema` 的 EX 增益，给出的是模型完全不碰非 gold 表
  能带来多少提升的上界。引用这个数字之前，先读下一节：这一档改变的不止
  一件事，而且至少在一个真实 corpus 上，它改变的那件事并不是选表本身。
- **`oracle_tables_padded`**——上一档的对照组。同样的 gold 表，额外填充
  一些从同一个 schema 里确定性选出的非 gold 表，让 prompt 大小基本不变，
  变的只是表的*身份*。阶梯里的其他任何一档都分不清"给对了表"和"给了一个
  更短的 prompt"这两件事的区别；这一档能。

  它填充到的是**检索表预算**（`retrieve` 的 `top_k`，默认 8），而不是
  schema 的表总数。这个区别就是这一臂的全部意义所在：如果填充到 schema
  的表总数，就会原样复现出 schema 那一档的 corpus，这一档也就悄悄退化
  成了 `oracle_schema`。目标被修正之前，实测曾经跑出过 11/11 张表、逐
  字节相同的上下文。在一个小到连预算都能装下全部表的 schema 上，这个
  对照根本没法起作用，这一行会用 `oracle_padding_degenerate` 标注出来。

收窄 corpus 的这三档——`oracle_schema`、`oracle_tables`、
`oracle_tables_padded`——是普通的臂：同一条 serve 路径，同一套护栏，
同一个评分器。唯一变化的是交给 `build_serve_rails()` 的那个 corpus，
模型调用本身没有任何被 mock 的部分，模型仍然要自己把查询写出来。这也是
它们的增益可信的原因：EX 不是一个模拟出来的数字，而是一个测出来的数字，
只是问题被刻意收窄过。

`oracle_sql` 不属于这一类。它压根不进 graph：没有模型调用、没有检索、
没有护栏层、没有 agent 循环。它把 gold SQL 直接交给评分器，所以它是
**对评分器的一次探针**，不是系统的一个臂，只共享最后一步。这正是它的
用处所在（把评分契约从其余一切里隔离出来），也正是它的数字答的是不同
问题的原因：它说明不了系统的行为。

## 解读增益

拿每一档去对照它下面那一档，而不是对照零：

- `oracle_sql − 1.0` 是评分缺口。如果它不是零，其余每一档的 EX（以及
  公平阶梯的 EX）都应该读作 `oracle_sql` 的一个分数，而不是这个评分器
  根本不存在的满分的一个分数。
- `oracle_schema − 公平阶梯里最好的那个臂的上限` 是 schema 路由正在付出
  的代价，包括它对生成阶段的连带影响。
- `oracle_tables − oracle_schema` 限定的是模型完全不碰非 gold 表能带来
  多大好处的上界。它是分类体系里 `table_select` 这个类别的一个上界，不是
  一次归因——见下文。
- `oracle_tables_padded − oracle_schema` 是这个上界里能归到*具体是哪些
  表*头上的那一部分，此时 prompt 大小被大致固定住了。

因为这种收窄是叠加在一条其余部分不变的 serve 路径之上的，所以相邻两档
之间的差值里，已经折进了和下游一切东西的交互效应：模型仍然要针对收窄后
的 corpus 写 SQL，这段 SQL 仍然要走完整条流水线。这是一个分类计数永远
做不到的性质——`error_taxonomy` 能告诉你某一行上存在某个类别，却告诉
不了你，去掉它之后，同一行上其他类别会发生什么。

## `oracle_tables` 没有隔离出什么

这一档换掉的是一整个 corpus，而下游的一切都是这个 corpus 的函数。在一个
真实的 5-schema 评测 corpus 上，对 103 个问题做测量，从 `oracle_schema`
走到 `oracle_tables`，至少同时改变了六件事：

| | `oracle_schema` | `oracle_tables` |
|---|---:|---:|
| 渲染出的上下文（中位数，字符数） | 7,899 | 4,079 |
| 已授权表（中位数） | 7 | 2 |
| 提供的连接边（中位数） | 8 | 2 |
| `suspect` 列警示（中位数） | 18 | 8 |

已授权表集合的收缩，不是一次信息上的变化，而是一次*强制执行*上的变化：
`allowed_tables` 跟着一起收缩，选错表的 SQL 不再只是不太可能发生，而是
直接被拦下。而真正起决定作用的数字并不在这张表里——103 个问题里的
103 个，`oracle_schema` **早就已经把每一张 gold 表都授权了**。检索层面
根本没有留下任何选表错误给这一档去消除，所以在这个 corpus 上，全部增益
来自三件事：剔除干扰表、连接关系被直接摆好，以及 prompt 变短。

所以"选表"这个说法其实指的是两件不同的事，而这一档只碰到了其中一件：

1. **检索与授权圈定一个邻域。** 这里的 recall 早就是 100%，没有什么可修的。
2. **模型在这个邻域内部挑表。** 错误就出在这里，而这一档消除错误的方式，
   是让它变得不可能发生，而不是让模型学会挑得更好。

这依然测出了一件值得知道的事——它是 `table_select` 这个错误类别诚实的
上界——但它是一个强制执行意义上的上界，不是一个检索意义上的上界，也没法
归到单一某个机制头上。

有两件事能让这个数字变得可解读，而不只是可疑。每一行 oracle 产出都会分别
记录 `oracle_gold_tables`（gold 实际读到的表）和 `oracle_offered_tables`
（这一档真正交出去的表——在 `oracle_tables` 上两者相同，在填充档上则是
gold 加上干扰表）。把 `oracle_gold_tables` 拿去和公平臂在同一个问题上
记录的 `licensed_tables` 做对照：如果授权早就已经覆盖了每一张 gold 表，
那这一档就没有消除任何选表错误，它的增益另有来源。两个字段之所以分开，
正是因为把它们并成一个，会让上面这项检查恰好在最需要它的那一档上出错。

而 `oracle_tables_padded` 则把剩下的这个上界进一步拆开：如果它的得分和
`oracle_tables` 一样，效应来自表的身份；如果它的得分和 `oracle_schema`
一样，效应从头到尾都只是 prompt 大小。凡是 `oracle_padding_degenerate`
为真的行都要跳过——这个对照在两端都会塌陷到某个邻档上：预算能装下整个
schema 时塌陷成 `oracle_schema`，gold 本身就已经占满预算时塌陷成
`oracle_tables`，两种情况都说明不了任何关于表身份的事情。

还有一条和读数有关的实现细节。在一个按表收窄的档上，few-shot 不仅按
schema 过滤，也按表过滤。在这层过滤生效之前，渲染进 `oracle_tables`
prompt 里的样例中有 73.7% 引用了这一轮被禁止使用的表——也就是说，这一档
一边把 gold SQL 展示给模型看，一边又会因为模型模仿它而惩罚模型，这会
拉低它的 EX，而原因和它本该单独隔离出来的那个阶段毫无关系。

## 硬性规则：只做诊断，绝不是产品数字

每一档从设计上都是"知道测试答案"的。`restrict_corpus()` 是从
`gold_tables_for(gold_sql)` 构建出收窄后的 corpus 的——这个 corpus 是
照着答案表构建出来的，而这恰恰是生产环境的 serve 路径永远不会有的东西。
把一个 oracle 档的 EX 当成系统性能来报告，等于报告一个这套系统在不先
知道答案的情况下根本产出不了的数字。

所以 `OracleRung` 在 `eval.arms.Arm` 里没有对应成员：`Arm` 是
公平阶梯（`baseline`、`curated`、`curated_sme`），是一个真实的 serve
配置能够跑出来的东西，把 oracle 档排除在这个枚举之外，正是为了防止它们
的数字被不小心当成公平阶梯的结果引用——不存在 `Arm.oracle_schema` 这种
东西，让一张粗心的对比表去误取。
`tests/test_oracle_and_probes.py::test_oracle_rungs_are_not_members_of_the_fair_arm_ladder`
把这两个枚举钉死为互不相交。一个 oracle 档产出的每一行，也都会在元数据
里打上 `oracle_rung`，这样即便脱离了这条枚举检查，这些运行产出的行事后
也不会被误认成某个普通臂的行。

## 一档如何运行

`oracle_solver(rung, corpus, gateway, settings, identity, model=..., gold=...)`
返回的求解器，遵循的是和公平阶梯的 `agent_solver` 相同的 `MetaSolver`
协议（`solve_with_meta`），所以它走的是同一套打分代码（`run_arm` /
池化驱动器按臂的那个循环），而不是另一条可能悄悄和它产生分歧的平行路径。

- **`GoldIndex`** 按问题*文本*去查 gold，因为 `MetaSolver` 协议就是
  `solve(question)`，没有 id。只有当"文本到 gold"的映射没有歧义时，
  这样做才安全，而在这个基准测试上，它几乎就不安全：有五个问题在训练集
  和测试集里都出现过，文本逐字节相同。`GoldIndex.build()` 容忍这种情况
  （这五个问题共享同一份 gold SQL），但遇到真正的冲突——两个问题文本
  相同、gold 却*不同*——会直接报错，而不是悄悄选一个，因为悄悄选一个，
  就等于把另一个问题的答案塞给了这个问题，让它本该衡量的那一档虚高。
- **`restrict_corpus()`** 把一个 corpus 收窄到一个 schema，对
  `oracle_tables` 而言，还会进一步收窄到一个具体的表集合。依赖资产跟着
  它们的表走：一个连接如果两端没有同时保留下来，描述的就是一条通向虚无
  的边；一个指标如果建立在一张被丢弃的表上，宣称的就是模型根本够不到的
  一列——两者都会跟着各自的表一起被丢弃。术语、笔记、few-shot 则原样
  保留——它们由自己的一套机制来限定范围，在这里去裁剪它们，改变的就
  不只是一档本该单独隔离出来的那一个变量了。如果指定的表一个都不匹配，
  结果是一个空 corpus，而不是悄悄回退到完整的那一份——回退会让这一档
  实际上什么都没测，看起来却像是跑过了。
- **`oracle_solver()`** 对 `oracle_sql` 从不调用模型——它直接返回 gold
  SQL。对另外三档，它为每一个不同的收窄后 corpus 构建一张受治理的
  serve 图（`build_serve_rails`）并缓存起来：`oracle_schema` 最多只需要
  给数据湖里的每个 schema 建一张图，而 `oracle_tables` 大致上每个问题
  都需要一张，因为 gold 的表集合很少重复。相对一次模型调用而言，构图的
  开销不大，但也不是免费的——这正是信息量最大的这一档，诚实的成本所在。

## 跑一档

池化驱动器接受 `--oracle`，可以用逗号分隔重复传入：

```bash
uv run python -m governed_bi.eval.run_datalake --oracle oracle_sql,oracle_schema
```

一个认不出来的档名会直接报错，而不是回退——这和提示词 registry 遵循的
是同一条规则，原因也一样：一个悄悄跑成了别的东西的拼写错误，会产出一个
没人能追溯的数字。

档会追加在公平臂*之后*，这样一次中途挂掉的运行仍然能保住自己的打分
结果；丢掉的只是诊断信息。即便在 `--workers N` 下，档也会串行运行，
因为每一档都要为收窄后的 corpus 重新建图，没法共享按臂划分的 worker
工厂。

单 schema 驱动器 `run_experiment.py` 没有对应的开关。反正那里有一档本来
就是退化的：既然已经钉死了一个 schema，`oracle_schema` 就是普通的臂。

每一行 oracle 产出都打上了 `oracle_rung`，这样它的数字事后不会被误认成
一个产品指标。

## 路由是被绕过，不是失败

把 corpus 钉死到一个 schema 之后，路由器只剩一个候选，于是它根本不会启动，
也就不会留下任何路由 provenance。照字面读，这一档的每一行都是
`routed_hit=False`，错误分类体系随即把所有错误答案都记到选择器头上。一个
存在目的就是消除路由误差的档，反过来报告说路由是全部问题。守卫加进去之前，
第一次活跑就是这样：`oracle_schema` 返回的是
`by_error_stage={'schema_pick': 5}`。

所以现在一档会把自己钉死的那个 schema 报告为路由结果——这才是诚实的值
（这里的路由按构造就是对的）——并置上 `routing_bypassed`，让"绕过"这件事
是明写出来的，而不是靠一个高得可疑的 `routing_recall` 去反推。
`attribute_row()` 会跳过这些行的路由归因。

同一条守卫也覆盖池子里因为别的原因只剩一个 schema 的情况，包括
`--limit-dbs 1`，以及构建时把其余数据库都掉光了。凡是 `total_schemas`
小于等于 1 的行都按绕过处理，因为那里的路由器同样没被问过任何问题。
